# 通用适配与验证结果的含义

## “6 个未确认”是什么

它指 `0x913188…fa6d` 项目的 847 个函数中，有 6 个函数的原字节码与重编译字节码
未能由当前实验性比较器建立对应关系。涉及引用别名、操作配对和枚举解包。
这不是 6 个编译错误，也不是已查明的 6 个业务逻辑错误；同样不能算已验证正确。
其余函数通过的是规范化指令或限定模型检查，不是完整 Move VM 等价证明。

## “完整模块字节码一致 5/37”是什么

比较单位是整个模块，而不是单个函数。37 个原始模块重新编译后，5 个模块完整一致，
32 个模块不一致。模块包含函数代码、常量池、类型/函数/地址表、权限声明等。
一个模块只要有一处差异，就不计入完整一致。
因此这个比例不是“只有 5 个模块能运行”，也不是“另外 32 个模块都错了”。
编译器、代码生成形式、表的排列和真正的逻辑变化都可能造成不一致；必须逐项核对，
不能把所有差异一律视作无害。当前样本还存在两个空模块的 friend 元数据差异。

## 适配规则不是按合约白名单执行

关键字转义、枚举模式恢复、互补条件的完整分支恢复、可变借用保留及求值顺序保护，
都作用于语法树和字节码指令，不根据用户的 Package ID、模块名或函数名选择是否修复。
真实合约的名称只用于测试样本和故障定位。不会为某个合约关闭覆盖校验或给模型失败放行。

2026-11-03 的跨项目验证范围：

| 样本 | 构建范围 | 函数比较范围 |
| --- | --- | --- |
| authority 主包及依赖 | 37 模块，两种导出 | 847 个函数，6 个未确认 |
| optimizer 主包及依赖 | 37 模块，两种导出 | 1067 个函数，模型内全部匹配 |
| efbfd 项目 | 38 模块，原地址导出 | 295 个函数，模型内全部匹配 |
| 独立数学包 | 10 模块，两种导出 | 168 个函数，模型内全部匹配 |

数学包此前只构建 `modular_bounds` 一个模块，并加入测试调用者保留 friend 表。
新的完整包回归直接导出全部 10 个真实模块，不添加模拟调用者。
`amm_math`、`sqrt` 此前的确定赋值问题已经由通用条件恢复规则解决。
完整包回归保留实际权限检查和 168 个函数的比较，不以孤立模块成功替代整包成功。

四组回归均加入 Linux CI。CI 绿色意味着所列检查通过，不意味着所有未来合约都受支持；
authority 的构建回归和它尚未通过的严格逻辑比较继续分别记录。
测试命令没有恢复原作者业务用例，不能代替业务测试。

## 扩展到更多合约

对完整单包、仅依赖系统包的原始字节码 fixture，可使用通用 runner：

```sh
cargo build --bin verify_package --bin compare_project
npx tsx scripts/test-standalone-roundtrip.ts <fixture.json> <new-output-directory>
```

该 runner 不筛选模块名或函数名，自动构建两种导出，核对原始字节码 SHA-256、权限、
模块数量和全部函数。缺失普通依赖时会失败，不能把不完整依赖图算成成功。
含普通依赖的项目使用 `scripts/test-optimizer-roundtrip.ts --fixture <project-fixture.json>`；
脚本虽然沿用首个回归的文件名，但主包、依赖及验证数量均从 fixture 读取。

```sh
npm run test:math-roundtrip
npm run test:roundtrip
npm run test:optimizer-roundtrip
npm run test:authority-build
```

通用适配的目标是不断扩展经过验证的字节码与语法规则、把新缺陷加入回归，覆盖不完整或
结构化失败时拒绝导出，语义未证实则保留未验证状态。
“所有合约无条件成功、全部逻辑等价”不是目前已有证据支持的承诺。
完整等价的验证标准和当前失败记录见 [官方源码与逻辑等价验证](source-equivalence.md)。
